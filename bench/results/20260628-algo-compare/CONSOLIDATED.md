# 压缩算法横向对比 — claude-projects append-only jsonl

测量日期 2026-06-28 · 语料 旗舰 96.4MB 单 jsonl（13760 行，mean 7.3KB/p50 3.4KB/p99 50KB/max 179KB）· 单线程计时 · tmpfs 消除磁盘 IO。工具版本见 `TOOL-VERSIONS.md`。

## 块大小先于算法：64KiB 是错的

boilerplate（系统提示/CLAUDE.md/工具 schema/历史重录）复现间距 p50=21KiB、**p90=154KiB**、max 12.5MB。64KiB 块只逮到 p50 以下的复现，砍掉绝大部分长程冗余。覆盖 p90 需 ≥256KiB，逼近整流上界需 ≥2–4MiB。块必须**行对齐**（FS 在行边界封块）。故算法对比只在 256KiB–4MiB 行对齐块上才有意义。

## 整流（封存/归档，随机访问上界）

| algo | ratio | 压 MB/s | 解 MB/s |
|---|---|---|---|
| xz -9e | 37.7x | 4 | 678 |
| zstd -19 --long=27 | 35.5x | 8 | **994** |
| brotli q11 | 35.1x | 1 | 1531 |
| zstd -19 | 29.9x | 8 | 1900 |
| zstd -3 | 21.3x | 730 | 2043 |
| bzip2 -9 | 15.0x | 12 | 51 |
| lz4 -9 | 12.3x | 919 | 2259 |
| gzip -9 | 9.2x | 68 | 341 |

xz 比值最高但解压最慢；**zstd-19 --long 以 ~5% 的比值差换来 1.5x 解压速度**，封存场景更优。brotli q11 压 1MB/s 不实用。

## 行对齐独立块（FS 实时读写，决策关键）

ratio 透视（行=算法，列=块大小）：

```
algo/level     256K    512K   1024K   2048K   4096K
lz4 -9          9.8x   10.9x   11.7x   12.1x   12.2x
zstd -3        12.0x   14.5x   16.7x   18.6x   19.9x
zstd -19       13.8x   16.8x   19.6x   22.0x   24.5x
brotli -q11    15.7x   19.1x   22.1x   24.8x   27.4x
xz -9e         14.4x   17.6x   20.6x   23.2x   25.8x
```

排序在所有块大小恒定：brotli > xz > zstd-19 > zstd-3 > lz4。但 brotli/xz 的比值优势（~10–12%）以 2–3x 慢解压、5–30x 慢压缩换来。

## 结论（针对 zipfs）

1. **算法选 zstd**——读密集 FS 靠解压吞吐活命，zstd 解压 1900–2165 MB/s 占住 Pareto 前沿。xz/brotli 多压 ~10% 但读慢 2–3x、封块慢 5–30x。
2. **退役 64KiB**；实时块取 **1MiB（zstd-19 → 19.6x）** 为甜点，要更高比值上 2–4MiB。
3. **lz4** 仅当读延迟压倒一切、比值次要时用（解压最快但比值仅一半）。
4. **冷封存** 用 zstd-19 --long=27（35.5x，解压 994MB/s），优于 xz。
5. **gzip/bzip2 全程被支配**，移除候选。

**关键落地警示**：**zipfs 链接的是 Rust crate 而非这些 CLI**——实际产出取决于 crate 版本：`zstd`(包 libzstd，版本敏感)、`lz4_flex`(纯 Rust 重写，与参考 lz4 不同，通常比值略低且无 HC)、`brotli`、`xz2`(包 liblzma)。**这些数字是 C 参考实现的参照上界，落地前须用实际链接的 crate 版本复测。**
